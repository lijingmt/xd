# Xiand 单进程线程优化架构

## 结论

Xiand 始终运行一个 Pike 游戏进程、一个世界状态和一套存档归属，不采用多 Worker、网关分片或跨进程世界迁移。

本机 Pike 9.0.13 基准显示，100 个纯 Pike 计算任务使用线程比顺序执行慢约 8.5%；100 个 20ms 阻塞等待任务使用线程则有明显收益。因此线程的安全边界是“可复制的值和独立 I/O”，不是人物、房间或战斗对象。

## 执行模型

- 所有可能访问人物、房间、NPC、战斗、掉落、队伍、家园和存档对象的 HTTP 命令，按“账号锁 → 世界锁”的固定顺序单写执行。
- 命令入口同时校验当前线程必须是 Pike 主 Backend；来自工作线程的游戏命令直接拒绝，避免心跳与工作线程并发改写世界。
- 不再为普通命令逐请求创建 `Thread.Thread`。
- 文件读取和非关键审计日志使用 Pike 9 `Thread.Farm`，总上限 8 条工作线程、最多 2048 个待处理任务；读取池 7 条、日志池 1 条，二者互不阻塞。
- 线程池只接收字符串路径、字符串内容和整数限制，不接收游戏对象。
- 日志池保持单工作线程，既避免多个线程同时追加造成内容交错，也保持入队顺序。
- HTTP 静态文件使用 `Concurrent.Future.on_success`，读取完成后由主 Backend 回调响应；HTTP 请求对象不进入工作线程。
- 人物存档仍在世界线程生成并原子替换；不能在线程内读取正在变化的人物对象。

## 心跳与挂机预算

- 全局心跳每个切片最多处理 128 个对象，并在约 5ms 时间预算后让出 Backend。
- 一轮未完成时用零延迟 `call_out` 继续，不丢对象，也不改变对象自己的心跳间隔计数。
- 挂机对大房间采用 128 个对象的轮转扫描；扫描完当前房间前不会错误判定空图并换图。
- 采集源、掉落和战斗目标使用独立游标，避免大量地面物品让单次挂机刷新无限遍历。
- 游标绑定当前房间，移动、重新开启挂机或房间对象变化后会安全复位；可见怪数量跨切片累计，最后一片不会漏掉前面切片中的超等级怪。
- 1–69 级练级路线构建为启动期只读快照，查询返回副本。

## 缓存与背压

- 地图、任务和技能配置继续使用常驻守护进程索引，不在每条命令中重新读取文件。
- 登录密码优先读取在线人物内存；离线档案通过线程池读取并只缓存 2 秒。
- 读取队列上限 512、日志队列上限 1536、合计上限 2048；日志洪峰不能占满读取容量，超限时拒绝新的非关键日志，避免内存无界增长。
- 静态文件、任务 CSV 和离线登录档案均有最大读取大小与路径白名单。

## 运行监控

`/health` 提供以下容量数据：

- Backend 最近/最大延迟和 250ms 告警次数；
- 心跳对象数、切片数、延期切片、最近/最大周期耗时；
- 进程 CPU 使用率、70% 连续阈值和告警次数；
- 世界命令等待数、峰值、最大耗时和慢命令；
- 人物存档次数、失败数、慢存档和最大耗时；
- Thread.Farm 线程上限、待处理数、拒绝数、失败数和读写字节；
- 地图、任务、技能和挂机路线缓存规模。

只有当 CPU 连续达到 70%、Backend/心跳持续超过 250ms，或世界命令等待峰值持续增长时，才需要继续做容量评估；该告警不自动切换到多进程架构。

## 验证

`test_single_process_runtime_optimization.pike` 验证线程池、单写锁顺序、心跳预算、存档指标、配置缓存、挂机扫描和认证路径边界。`test_http_thread_architecture.pike` 验证旧的逐请求线程已移除，并检查健康状态和兼容入口。

`async_iod.pike` 的 Thread.Farm 是进程级常驻资源，没有热卸载协议；修改该守护进程必须走安全保存后的完整重启，不使用在线 destruct/reload。
